## Spotlight: Native OpenTelemetry (OTLP) Client-Side Tracing

When an API call is unexpectedly slow or fails intermittently, server-side logs only tell half the story—they show what happened after the request reached Google's frontend, not time spent inside your application on connection setup, credential refresh, retry backoff, or serialization.

A standout cross-catalog theme in October was the convergence on **OpenTelemetry (OTLP)** for client-side observability across **Secret Manager**, **Spanner**, **Memorystore**, **Google Kubernetes Engine**, and **Go instrumentation**. Because Google Cloud client libraries now discover an active OpenTelemetry `TracerProvider` natively, you no longer need product-specific tracing wrappers to see what your SDKs are doing under the hood.

Our new samples—which power the walkthrough in the [Python Client Library Observability Guide](https://docs.cloud.google.com/python/docs/observability)—walk through the progression from local debugging to production telemetry:
* **Local Console Debugging**: [`get_secret_version_trace.py`](https://github.com/GoogleCloudPlatform/python-docs-samples/blob/main/secretmanager/snippets/get_secret_version_trace.py) and [`get_secret_version_trace_async.py`](https://github.com/GoogleCloudPlatform/python-docs-samples/blob/main/secretmanager/snippets/get_secret_version_trace_async.py) show how to inspect client spans locally with `ConsoleSpanExporter`.
* **Cloud Trace & OTLP Export**: [`get_secret_version_trace_cloud_trace.py`](https://github.com/GoogleCloudPlatform/python-docs-samples/blob/main/secretmanager/snippets/get_secret_version_trace_cloud_trace.py) and Spanner's [`observability-traces-otlp.js`](https://github.com/GoogleCloudPlatform/nodejs-docs-samples/blob/main/spanner/observability-traces-otlp.js) configure `BatchSpanProcessor` with Cloud Trace or an OTLP gRPC collector endpoint.

### Extending the Samples: Tracing Multi-Product Workflows Under One Span

While each sample traces a single service, the real power of native OpenTelemetry support in `google-api-core` appears when an application workflow spans multiple Google Cloud products. Because `GOOGLE_SDK_PYTHON_TRACING_ENABLED="true"` activates tracing across all GAPIC client libraries in the process, wrapping calls to **Secret Manager** and **Firestore** inside a parent span automatically links both services' RPC spans under a single trace ID:

```python
import os
import sys

from google.api_core.exceptions import GoogleAPICallError
from google.cloud import firestore, secretmanager
from opentelemetry import trace
from opentelemetry.exporter.cloud_trace import CloudTraceSpanExporter
from opentelemetry.instrumentation.grpc import GrpcInstrumentorClient
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor


def verify_and_record_secret(
    project_id: str = "example-project-id",
    secret_id: str = "example-secret-id",
    database_id: str = "(default)",
) -> None:
    provider = TracerProvider()
    provider.add_span_processor(
        BatchSpanProcessor(CloudTraceSpanExporter(project_id=project_id))
    )
    trace.set_tracer_provider(provider)
    os.environ["GOOGLE_SDK_PYTHON_TRACING_ENABLED"] = "true"
    GrpcInstrumentorClient().instrument()

    tracer = trace.get_tracer("service.audit")
    secret_client = secretmanager.SecretManagerServiceClient()
    db = firestore.Client(project=project_id, database=database_id)
    name = f"projects/{project_id}/secrets/{secret_id}/versions/latest"

    try:
        with tracer.start_as_current_span("verify-and-record-secret"):
            version = secret_client.get_secret_version(request={"name": name})
            db.collection("secret_audits").document(secret_id).set(
                {
                    "secret_version": version.name,
                    "state": version.state.name,
                }
            )
            print(
                f"Recorded audit entry for {version.name} (state: {version.state.name})"
            )
    except GoogleAPICallError as err:
        print(
            f"error: failed to verify and record secret '{secret_id}': {err.message}",
            file=sys.stderr,
        )
    finally:
        provider.shutdown()
```

Running `verify_and_record_secret` prints the application confirmation to `stdout` and exports a three-span waterfall under a single `trace_id` (`a1b2c3d4e5f60718293a4b5c6d7e8f90`), where both downstream product RPCs report the parent workflow's `span_id` (`0x1020304050607080`) as their `parent_id`:

```text
Recorded audit entry for projects/example-project-id/secrets/example-secret-id/versions/1 (state: ENABLED)

Trace ID: a1b2c3d4e5f60718293a4b5c6d7e8f90
└── verify-and-record-secret (SpanKind.INTERNAL, span_id: 0x1020304050607080, parent_id: None) — 754ms
    ├── /google.cloud.secretmanager.v1.SecretManagerService/GetSecretVersion
    │   (SpanKind.CLIENT, span_id: 0x1122334455667788, parent_id: 0x1020304050607080, rpc.grpc.status_code: 0) — 268ms
    └── /google.firestore.v1.Firestore/Commit
        (SpanKind.CLIENT, span_id: 0x99aabbccddeeff00, parent_id: 0x1020304050607080, rpc.grpc.status_code: 0) — 481ms
```

Instead of correlating separate log lines by timestamp, a single trace in Cloud Trace (or any OTLP backend) immediately shows that `268ms` of the `754ms` workflow was spent fetching the secret metadata from Secret Manager and `481ms` was spent committing the audit document to Firestore.

## Modernizing Kotlin Samples

In October, we also noticed that the legacy `kotlin-samples` repository hadn't been updated in a while, so we took on modernizing and migrating foundational Kotlin samples across **Cloud Storage** ([`CreateBucket.kt`](https://github.com/GoogleCloudSamples/client-library-samples/blob/main/storage/v1/kotlin/google-cloud-storage/CreateBucket.kt), [`DownloadObject.kt`](https://github.com/GoogleCloudSamples/client-library-samples/blob/main/storage/v1/kotlin/google-cloud-storage/DownloadObject.kt)), **Pub/Sub** ([`CreateSubscription.kt`](https://github.com/GoogleCloudSamples/client-library-samples/blob/main/pubsub/v1/kotlin/google-cloud-pubsub/CreateSubscription.kt), [`SubscribeAsync.kt`](https://github.com/GoogleCloudSamples/client-library-samples/blob/main/pubsub/v1/kotlin/google-cloud-pubsub/SubscribeAsync.kt)), **Firestore** ([`SetDocument.kt`](https://github.com/GoogleCloudSamples/client-library-samples/blob/main/firestore/v1/kotlin/google-cloud-firestore/SetDocument.kt), [`GetCollectionDocuments.kt`](https://github.com/GoogleCloudSamples/client-library-samples/blob/main/firestore/v1/kotlin/google-cloud-firestore/GetCollectionDocuments.kt)), and **Cloud Vision** ([`AnnotateImage.kt`](https://github.com/GoogleCloudSamples/client-library-samples/blob/main/vision/v1/kotlin/google-cloud-vision/AnnotateImage.kt)) into [`GoogleCloudSamples/client-library-samples`](https://github.com/GoogleCloudSamples/client-library-samples).

Rather than lifting and shifting old code, we rebuilt each sample around our [Effective Samples](../docs/effective-samples/_index.md) standards on JDK 21 and Gradle 8.10:

* **Copy-paste-callable functions** with minimal, environment-specific arguments (`projectId`, `bucketName`) and inline behavioral defaults.
* **Idiomatic Kotlin resource management**, using `.use {}` for `AutoCloseable` service clients and structured `finally` blocks (`subscriber?.stopAsync()?.awaitTerminated()`) for asynchronous streams.
* **Actionable error handling**, catching specific API exceptions (`StorageException`, `InvalidArgumentException`) and logging contextual diagnostics to `stderr`.

For example, in [`CreateBucket.kt`](https://github.com/GoogleCloudSamples/client-library-samples/blob/main/storage/v1/kotlin/google-cloud-storage/CreateBucket.kt), scoping the `Storage` client with `.use {}` guarantees connection cleanup while `StorageException` inspection distinguishes a `409 Conflict` from general API failures:

```kotlin
options.service.use { storage ->
  val bucket = storage.create(bucketInfo)
  println("Created bucket ${bucket.name} in ${bucket.location} (${bucket.storageClass})")
}
```
